# LAGD FPGA flow (Xilinx / ZCU102)

Deploys the **digital** LAGD SoC on a Xilinx **ZCU102** to bring up and test the
**SPI-slave, JTAG and UART** interfaces against an external driver board (a
Zedboard, over FMC). It is **not** the chip: pads, the analog PLL, and the
`galena` analog macro are replaced by FPGA-friendly equivalents.

## Board

| FPGA | Sys clock | Config |
|---|---|---|
| `xczu9eg-ffvb1156-2-e` (Zynq US+ MPSoC ZU9EG) | 300 MHz diff (`user_si570_sysclk`, AL8/AL7) | PL-only, JTAG |

ZCU102 is an MPSoC: this is a **PL-only** design (the hard PS is not used), so it
is configured over **JTAG** (`make program`) rather than booted from SD/QSPI.
The flow is still board-parameterized (`common.tcl` part, `impl_ip.tcl` clk_wiz,
`constraints/zcu102.xdc` pins), so a second board could be re-added later.

## What runs on the FPGA

The top is [`lagd_fpga`](../../hw/rtl/fpga/lagd_fpga.sv) (instead of the silicon
`lagd_chip`). It instantiates `lagd_soc` and replaces the silicon-only pieces:

| Silicon piece | FPGA replacement |
|---|---|
| IO pads | `IBUFDS` (clock) + `IOBUF` (SPI data) |
| Analog PLL (`lagd_clk_gen`) | Xilinx `clk_wiz` (RTC comes in on `rtc_i`) |
| `galena` analog macro | [`galena_fpga_stub`](../../hw/rtl/fpga/galena_fpga_stub.sv) (constant tie-off; ising cores present but inert) |
| tsmc `tc_sram` | `tech_cells_generic` `tc_sram_xilinx` (BRAM) |

The AXI/register address map is identical to silicon, so driver software hits
the same addresses.

## Clocks

- **soc_clk**: generated by `clk_wiz` from the 300 MHz board clock
  (`user_si570_sysclk`). Currently **50 MHz** (`CLKOUT1_REQUESTED_OUT_FREQ` in
  `scripts/impl_ip.tcl`) — cheshire's reference rate, chosen for reliable CVA6
  timing closure. The interfaces are asynchronous to `soc_clk`, so its rate does
  not affect interface correctness.
- **rtc**: external input `rtc_i` from the driver board (<= 32.768 kHz), like
  the chip's `pad_rtc_i`.
- **spi_sck / jtag_tck / rtc_i**: externally driven; declared as clocks in
  `constraints/lagd.xdc` and grouped asynchronous to `soc_clk`.

## Layout

```
target/xilinx/
├── Makefile                       # sources / ips / bitstream / program / clean
├── constraints/
│   ├── lagd.xdc                   # board-independent timing (clocks, async groups)
│   └── zcu102.xdc                 # ZCU102 pins (clock/reset/UART + FMC mapping)
└── scripts/
    ├── common.tcl                 # board params + helpers
    ├── impl_ip.tcl                # build clk_wiz IP
    ├── impl_sys.tcl               # project + synth + impl + bitstream
    ├── add_sources.zcu102.tcl     # generated by bender (gitignored)
    └── util/program.tcl           # program the board
```
Generated `build/`, `out/`, and `add_sources.*.tcl` are gitignored.

## Build

```bash
cd target/xilinx
make sources     # bender -> add_sources.zcu102.tcl
make ips         # build the clk_wiz IP
make synth       # synthesis only (no FMC pins needed) - utilization/timing check
make bitstream   # clk_wiz IP + synth + impl -> out/lagd.zcu102.bit
make program     # configure the FPGA over the HW server (JTAG)
```
`make synth` stops after synthesis (set via `LAGD_STOP_AFTER_SYNTH`), so it runs
before the FMC pin assignments are known. `make bitstream` needs every port
pinned. Override the tool or HW-server via `make` variables (`VIVADO=`,
`HWS_URL=`).

The bender source list is selected with `-t fpga -t xilinx -t rtl -t cva6
-t cv64a6_imafdcsclic_sv39` (`rtl` pulls iDMA's synthesizable RTL, incl.
`idma_pkg`). `bender script vivado` implicitly activates
`synthesis`+`fpga`+`xilinx`; the ASIC-only source groups in `Bender.yml` are
gated with `not(fpga)` so pads/PLL/tech-cells stay out of the FPGA build.

## Pin assignment

`constraints/zcu102.xdc` is fully populated (from the ZCU102 v3.4 board files and
the driver's `xillydemo.xdc`):

- **clock / reset / UART**: on-board (`user_si570_sysclk` AL8/AL7, CPU_RESET
  AM13, PL USB-UART F13/E13).
- **SPI / RTC / boot straps** (device under test): from the **Zedboard** driver
  over FMC. Balls are the ZCU102 **HPC0** locations for the same FMC LA pins the
  Zedboard uses in `xillydemo.xdc` (LA<n> -> LA<n> over the cable).
- **JTAG**: not routed by the driver and no spare FMC pins, so parked on onboard
  DIP switches / an LED; the real bring-up preloads over **SPI** (passive boot).

Hardware note: the Zedboard (FMC-LPC) and ZCU102 (FMC-HPC) are both carriers, so
they need a **male-to-male FMC-to-FMC cable** (pin-preserving); VADJ_FMC must be
**1.8 V** on the ZCU102. See the header of `zcu102.xdc` for details.

Synthesis (`make synth`) runs without any pins (good for an early
utilization/timing check); implementation needs every port pinned.
