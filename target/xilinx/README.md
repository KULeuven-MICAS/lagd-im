# LAGD FPGA flow (Xilinx / ZCU102)

Author: Jiacong Sun \<jiacong.sun@kuleuven.be\>

Date: 2026/07/18

Deploys the **digital** LAGD SoC on a Xilinx **ZCU102** to bring up and test the
**SPI-slave, JTAG and UART** interfaces against an external driver board (a
Zedboard, over FMC). It is **not** the chip: pads, the analog PLL, and the
`galena` analog macro are replaced by FPGA-friendly equivalents.

The user guide of ZCU102 can be found online at [here](https://docs.amd.com/v/u/en-US/ug1182-zcu102-eval-bd).

To control the PS of ZCU102 on a Windows computer via UART cable, please download first its UART driver (CP210x Universal Windows Driver) at [here](https://www.silabs.com/software-and-tools/usb-to-uart-bridge-vcp-drivers?tab=downloads). Then, software (e.g., MobaXterm) can open its interface with baudrate 115200.

To set the ZCU102's pins/FMC voltage, please use the Windows OS, download its SCUI (only works under a Windows OS) at [here](https://account.amd.com/en/forms/downloads/license-form-tip.html?cid=ef381bff-c447-4222-9049-49b8ea9a6e8b&filename=xtp428-zcu102-bit-c-2019-1_cluster.zip&license=eula-design-license), and install Vivado (needed by SCUI).

Since the Cheshire's BootROM will not return to the idle state after finishing a program, we need to reload the bitstream on the PL (programming logic) everytime. To do this earsier, it is suggested to use a SD Card (with Petalinux) to boot the ZCU102, so that you can reload the bitstream on the PL in a Jupyter notebook. If you have no experience on how to do it, we also support to directly program the PL via JTAG cable (Use `make program`. See the description below)

## Board

| FPGA | Sys clock | Config |
|---|---|---|
| `xczu9eg-ffvb1156-2-e` (Zynq US+ MPSoC ZU9EG) | 300 MHz diff (`user_si570_sysclk`, AL8/AL7) | PL-only, JTAG |

ZCU102 is an MPSoC: this is a **PL-only** design (the hard PS is not used), so it
is configured over **JTAG** (`make program`) rather than booted from SD/QSPI.
The flow is still board-parameterized (`common.tcl` part, `impl_ip.tcl` clk_wiz,
`constraints/zcu102.xdc` pins), so a second board could be re-added later.

## What runs on the FPGA

The top is [`lagd_fpga`](../../hw/rtl/fpga/lagd_fpga.sv) (instead of the silicon
`lagd_chip`). It instantiates `lagd_soc` and replaces the silicon-only pieces:

| Silicon piece | FPGA replacement |
|---|---|
| IO pads | `IBUFDS` (clock) + `IOBUF` (SPI data) |
| Analog PLL (`lagd_clk_gen`) | Xilinx `clk_wiz` (RTC comes in on `rtc_i`) |
| `galena` analog macro | [`galena_fpga_stub`](../../hw/rtl/fpga/galena_fpga_stub.sv) (mostly tie-off, `bct_read_o` tapped from `wbl_i`; ising cores present but inert) |
| tsmc `tc_sram` | `tech_cells_generic` `tc_sram_xilinx` (BRAM) |

The AXI/register address map is identical to silicon, so driver software hits
the same addresses.

## Clocks

- **soc_clk**: generated by `clk_wiz` from the 300 MHz board clock
  (`user_si570_sysclk`). Currently **50 MHz** (`CLKOUT1_REQUESTED_OUT_FREQ` in
  `scripts/impl_ip.tcl`) — cheshire's reference rate, chosen for reliable CVA6
  timing closure. The interfaces are asynchronous to `soc_clk`, so its rate does
  not affect interface correctness.
- **rtc**: external input `rtc_i` from the driver board (<= 32.768 kHz), like
  the chip's `pad_rtc_i`. In **standalone** builds (see below) this is instead
  generated on-FPGA by dividing `soc_clk` (÷763 → ~32.768 kHz); it is only
  sampled by the CLINT (2-FF synchronizer + edge detect in `soc_clk`), never used
  as a clock, so it needs no BUFG or timing constraint.
- **spi_sck / jtag_tck / rtc_i**: externally driven; declared as clocks in
  `constraints/lagd.xdc` and grouped asynchronous to `soc_clk`. The routed
  reports confirm the grouping works (empty Inter Clock Table — see [Status](#status)).
- **spi_sck / jtag_tck land on non-clock-capable (non-GCIO) pins** but drive
  global buffers, so the placer needs the `CLOCK_DEDICATED_ROUTE FALSE`
  overrides in `constraints/zcu102_impl.xdc` — without them it fails with
  `[Place 30-675]`. This is safe here: both are slow (25 MHz SPI, 10 MHz TCK)
  and asynchronous to `soc_clk`, crossing through CDCs, so the less predictable
  clock insertion delay does not matter. Driving SPI SCK from LA00_CC/LA01_CC
  (which *are* clock-capable on the ZCU102) would remove the need, but requires
  a driver-board change. See the header of `zcu102_impl.xdc`.

## Layout

```
target/xilinx/
├── Makefile                       # sources / ips / synth / bitstream / impl / program / clean
├── constraints/
│   ├── lagd.xdc                   # board-independent timing (clocks, async groups)
│   ├── zcu102.xdc                 # ZCU102 pins (clock/reset/UART + FMC mapping)
│   └── zcu102_impl.xdc            # impl-only: CLOCK_DEDICATED_ROUTE overrides
└── scripts/
    ├── common.tcl                 # board params + helpers
    ├── impl_ip.tcl                # build clk_wiz IP
    ├── impl_sys.tcl               # project + synth + impl + bitstream (make bitstream)
    ├── impl_only.tcl              # re-impl from the synth checkpoint (make impl)
    ├── add_sources.zcu102.tcl     # generated by bender (gitignored)
    ├── util/program.tcl           # program the board
    └── util/list_hw.tcl           # diagnostic: list JTAG targets (make list-hw)
```
Generated `build/`, `out/`, `tmp/`, and `add_sources.*.tcl` are gitignored.
Timing and utilization reports land in `build/zcu102.lagd/reports.impl/` (and
`reports.synth/` for `make synth`).

## Build

```bash
cd target/xilinx
make sources     # bender -> add_sources.zcu102.tcl
make ips         # build the clk_wiz IP
make synth 2>&1 | tee synth.log # synthesis only (no FMC pins needed) - utilization/timing check
make impl 2>&1 | tee impl.log # implement and generate bitstream, reusing the synthesis checkpoint
make program     # configure the FPGA over the HW server (JTAG)
make list-hw     # diagnostic: list JTAG targets/devices (read-only, does not program)
```

`make list-hw` is a standalone read-only helper for when programming fails or a
server hosts several boards: it prints the hardware targets and the JTAG chain
(expect device `xczu9_0` for the ZCU102). An empty list (`NO TARGETS`) points to
a powered/cabled/driver/hw_server problem rather than a bitstream one. Pin a
specific board with `make list-hw HWS_URL=<host>:3121`, then
`make program HWS_PATH=xilinx_tcf/Digilent/<serial>`.

Or simply run:

```bash
make bitstream LAGD_STANDALONE=1   # clk_wiz IP + synth + impl -> out/lagd.zcu102.bit  (~85 min)
```

`LAGD_STANDALONE=1` is used for FPGA verification, which disables the RTS/CTS of UART interface.

`make synth` stops after synthesis (set via `LAGD_STOP_AFTER_SYNTH`), so it runs
before the FMC pin assignments are known. `make bitstream` needs every port
pinned. Override the tool or HW-server via `make` variables (`VIVADO=`,
`HWS_URL=`).

### Fast iteration

`make bitstream` always rebuilds the project from scratch (`create_project
-force`), so it re-runs synthesis (~26 min) even when only pins changed. When
**only implementation-affecting inputs changed** (pins, `zcu102_impl.xdc`,
strategy), use `make impl` instead: it opens the existing `synth_1` checkpoint
and runs only opt/place/route/bitstream.

> ⚠️ `make impl` does **not** check whether the RTL is newer than the
> checkpoint. If the RTL or the bender source list changed, run `make bitstream`
> — otherwise you will implement a stale netlist.

> ⚠️ `make impl` links IPs from their out-of-context `.dcp` rather than their
> `.xci`, so the IP's *own* constraints are not applied (Vivado warns
> `[Vivado 12-5469]` and `[Project 1-840]`). **Produce the final bitstream with
> `make bitstream`**, which goes through `read_ip` and applies them properly.
>
> For the current `clk_wiz` the measured gap is small: its entire constraint set
> is one property (`PHASESHIFT_MODE LATENCY` on the MMCM, in `clkwiz.xdc` —
> `clkwiz_board.xdc` and `clkwiz_late.xdc` are empty), and the MMCM output clock
> is auto-derived correctly at 19.998 ns / 50.005 MHz. Re-check this if the IP
> configuration changes.

Implementation dominates the runtime, so `make impl` saves less than it sounds —
roughly 30 min of an ~85 min `make bitstream` (Measured 2026-07-15, 8 threads):

| Phase | Elapsed |
|---|---|
| `opt_design` | 3.6 min |
| `place_design` | 21.0 min |
| `phys_opt_design` | 1.3 min |
| `route_design` | 21.2 min |
| `write_bitstream` | 1.6 min |
| **`make impl` total** | **~55 min** |

`clocks.rpt` is generated by a full RTL elaboration (~4 min) whose only output is
that report, so it is opt-in: `make bitstream LAGD_CLOCKS_RPT=1`.

### Standalone (no driver board)

By default `rtc_i` and `boot_mode_i` come from the Zedboard driver over the FMC,
matching silicon. To bring the ZCU102 up on its own — no FMC cable — build with:

```bash
make bitstream LAGD_STANDALONE=1
```

This sets the `Standalone` generic on `lagd_fpga`, which generates the RTC
on-FPGA (`soc_clk` ÷763 ≈ 32.768 kHz) and forces `boot_mode = 00` (passive boot).
You then program over JTAG (`make program`) and preload over the ZCU102's own
USB-UART. The `rtc_i`/`boot_mode_i` **pins still exist and are constrained** in
both modes — in standalone they are simply ignored — so no XDC change is needed.

Because it is a **synthesis-time** generic, it only takes effect through
`make bitstream` (or `make synth`); `make impl` reuses the existing checkpoint and
cannot switch modes. Without the FMC, the SPI-slave preload path is unavailable,
so use the UART debug protocol (`../lagd-meas/sw/uart/`) to load and run code.

Constraints are split so this works:

| File | Used in synthesis? | Contents |
|---|---|---|
| `lagd.xdc` | yes | board-independent timing (input clocks, async groups) |
| `zcu102.xdc` | yes | pins (clock/reset/UART/FMC) |
| `zcu102_impl.xdc` | **no** | `CLOCK_DEDICATED_ROUTE` overrides — reference post-synthesis net names |

Because `zcu102_impl.xdc` is marked `used_in_synthesis false`, editing it does
not invalidate `synth_1`, and it produces no "no nets matched" warnings during
synthesis.

The bender source list is selected with `-t fpga -t xilinx -t rtl -t cva6
-t cv64a6_imafdcsclic_sv39` (`rtl` pulls iDMA's synthesizable RTL, incl.
`idma_pkg`). `bender script vivado` implicitly activates
`synthesis`+`fpga`+`xilinx`; the ASIC-only source groups in `Bender.yml` are
gated with `not(fpga)` so pads/PLL/tech-cells stay out of the FPGA build.

## Pin assignment

`constraints/zcu102.xdc` is fully populated (from the ZCU102 v3.4 board files and
the driver's `xillydemo.xdc`):

- **clock / reset / UART**: on-board (`user_si570_sysclk` AL8/AL7, CPU_RESET
  AM13, PL USB-UART F13/E13).
- **SPI / RTC / boot straps** (device under test): from the **Zedboard** driver
  over FMC. Balls are the ZCU102 **HPC0** locations for the same FMC LA pins the
  Zedboard uses in `xillydemo.xdc` (LA<n> -> LA<n> over the cable).
- **JTAG**: not routed by the driver and no spare FMC pins, so parked on onboard
  DIP switches / an LED; the real bring-up preloads over **SPI** (passive boot).

Hardware note: the Zedboard (FMC-LPC) and ZCU102 (FMC-HPC) are both carriers, so
they need a **male-to-male FMC-to-FMC cable** (pin-preserving); VADJ_FMC must be
**1.8 V** on the ZCU102. See the header of `zcu102.xdc` for details.

Synthesis (`make synth`) runs without any pins (good for an early
utilization/timing check); implementation needs every port pinned.

## Status

The flow has been run end-to-end on **Vivado 2025.2** (2026-07-15): synthesis,
implementation, DRC and bitgen all complete with **0 errors**, producing
`out/lagd.zcu102.bit` (26.5 MB). The only critical warnings are the expected
black-box/`.dcp` notices documented in `impl_only.tcl`.

**Timing closes.** From `build/zcu102.lagd/reports.impl/timing_summary.rpt`
(design state Routed, `-2` speed grade, temperature grade E):

| Check | Worst slack | TNS | Failing endpoints |
|---|---|---|---|
| Setup | **+2.599 ns** | 0.000 | 0 / 397,159 |
| Hold | +0.010 ns | 0.000 | 0 / 397,159 |
| Pulse width | +0.500 ns | 0.000 | 0 / 129,436 |

> *"All user specified timing constraints are met."*

The critical clock is `clk_out1_clkwiz` (the 50 MHz soc_clk), closing at
+2.599 ns of its 19.998 ns period; `spi_sck` closes at +17.740 ns and `jtag_tck`
at +49.891 ns. The **Inter Clock Table is empty**, which confirms the
`set_clock_groups -asynchronous` in `lagd.xdc` is actually taking effect rather
than silently failing to match.

**Utilization** (`reports.impl/utilization.rpt`; device totals are ZU9EG
datasheet figures):

| Resource | Used | Device | ~% |
|---|---|---|---|
| LUTs | 179,750 | 274,080 | 66% |
| FFs | 129,023 | 548,160 | 24% |
| RAMB36 | 388 | 912 | 43% |
| DSPs | 27 | 2,520 | 1% |

A single `ising_core_wrap` accounts for ~39k LUTs, ~31k FFs and 136 RAMB36 of
that, so LUTs are the resource to watch if the core count grows.

### Known gap: interface I/O timing is unconstrained

`check_timing` reports 11 input and 7 output ports with no `set_input_delay` /
`set_output_delay`, both at **HIGH** severity: `spi_sd_io[3:0]`, `spi_cs_i`,
`jtag_tdi_i`, `jtag_tms_i`, `jtag_tdo_o`, `uart_rx_i`, `uart_tx_o`,
`uart_cts_ni`, `uart_rts_no` and `boot_mode_i[1:0]`.

So "timing met" above covers the **internal logic only**. Setup/hold at the FPGA
pin, relative to the Zedboard-driven `spi_sck` / `jtag_tck`, is neither
constrained nor verified. The async clock groups keep the internal CDCs safe but
say nothing about pad-level timing. At 25 MHz SPI this is very likely fine — but
since preloading over SPI *is* the bring-up path, constrain these first if the
interfaces misbehave on hardware.

## Notes

- **Passive boot is one-shot.** After the preloaded program returns, the bootrom
  writes `(ret << 1) | 1` to `SCRATCH[2]` and parks the core in a `wfi` loop; it
  does **not** re-enter the poll loop, so writing a second entry point over SPI
  has no effect. Pulse **CPU_RESET** (AM13) to run another program — the ROM
  restarts and polls again. This is a core reset only; no FPGA reconfiguration
  (`make program`) is needed.
- If `bender` cannot read its cache (`safe.bareRepository` git error), prefix
  commands with
  `GIT_CONFIG_COUNT=1 GIT_CONFIG_KEY_0=safe.bareRepository GIT_CONFIG_VALUE_0=all`
  or run `git config --global --add safe.bareRepository all`.
